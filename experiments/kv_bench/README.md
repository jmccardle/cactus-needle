# KV-cache for Needle + 4-config decode benchmark

Implements the KV-cache split from `EXPORT_PATHS.md` for the stock Needle checkpoint and
benchmarks four decode configurations in prefill and generation tokens/s:

**stock** (no cache, no grammar) · **KV** (cache) · **JumpForward** (grammar, no cache) ·
**KV+JumpForward** (both).

## Result

| config | prefill tok/s | **gen tok/s** | fwd passes | total ms | end-to-end |
|---|---|---|---|---|---|
| stock (full-buffer) | 3,504 | **19** | 20.7 | 1229 | 1.0× |
| KV-cache | 1,881 | **123** | 20.7 | 477 | 2.6× |
| JumpForward | 3,504 | **33** | 11.6 | 786 | 1.6× |
| KV + JumpForward | 1,881 | **196** | 13.6 | 422 | 2.9× |

**Generation throughput (CPU): KV 6.6× × JumpForward 1.8× = 10.5× combined.** The two wins are
orthogonal and multiply — KV cuts the cost *per* forward pass, jump-forward cuts the *number*
of passes on the same output. (40 prompts, all 10 tools shown each call, greedy, CPU JAX.
`results.md` is regenerated by `bench.py`.)

> **On GPU this does not hold — see `../../GPU_NOTES.md` and `results_gpu.md`.** A full-buffer
> pass is only ~0.6 ms on a 4090, so at batch 1 the wall time is host/dispatch bound and the
> compute these tricks save is already free: KV drops to 1.1×, KV+JumpForward (1.2×) is *slower*
> than JumpForward alone (1.6×), and end-to-end latency is flat. The GPU lever is **batching**
> (`batched_throughput.py`: ~6× aggregate throughput to batch 16), not the decode tricks — the
> right combination is a *batched* KV-cache decode.

## What was implemented (`kv_model.py`)

The stock `run.py` re-runs the entire decoder over the full padded buffer every token, and
re-projects cross-attention K/V from the encoder output at every step. `KVNeedle` implements the
cache split the architecture was designed for:

- **encoder** runs once (reuses the flax encoder);
- **cross-attention K/V** are projected from the encoder output once per request and cached
  (`cross_kv`) — this is the bulk of what stock repeats every step;
- **decoder self-attention K/V** are cached and appended;
- a single **chunked `extend(tokens, start, …)`** processes *m* new tokens in parallel, writes
  their K/V to the cache, and returns logits. `m=1` is free decode; `m=len(run)` is a
  jump-forward forced run injected as one batched pass. jitted per chunk length.

Weights are read directly from the released checkpoint's `nn.scan`-stacked pytree; the math
mirrors `needle/model/architecture.py` (ZCRMSNorm, per-head q/k norm, GQA, half-split RoPE on
self-attention only, gated residuals, no FFN, tied embedding).

## Correctness

`parity.py` — KV-cached greedy decode vs stock full-buffer greedy decode: **49/50 exact match**
on CPU (**50/50 on GPU**) over a 50-example sample. The single CPU diff is a late-token near-tie
flip from computing in fp32 (this impl) vs bf16 (stock); the outputs are identical up to that
point. The cache split is correct — it is not an approximation, just a different schedule of the
same computation.

## Batched KV-cache (`kv_batch.py`) — the GPU throughput lever

`BatchKVNeedle` adds a batch axis to `KVNeedle` (encoder, cross-K/V, self-attn cache, chunked
`extend`). Because a cached decode step is O(1) in sequence length, aggregate throughput scales
with the batch instead of saturating like the un-cached full-buffer path — measured on a 4090:

| batch | agg gen tok/s | per-stream | peak GPU MB |
|---|---|---|---|
| 1 | 1,108 | 1,108 | 891 |
| 16 | 11,137 | 696 | 891 |
| 256 | **21,635** | 85 | 8,709 |

Batch-invariance and stock agreement both **20/20** (`batched_kv_bench.py`; full table in
`batched_kv_gpu.md`). This — batched cached decode + the union grammar from `../llguidance_poc`
+ a fine-tuned checkpoint — is the serving path for Needle as a classifier / structured-extraction
engine. See `../../GPU_NOTES.md` for the full CPU-vs-GPU story.

## Notes / caveats

- **Prefill vs generation tradeoff.** KV's prefill tok/s is *lower* (886 vs 1,503) because it
  front-loads the cross-K/V projection — but that is exactly the per-token work stock repeats
  every step, so end-to-end latency still drops (1558→866 ms). The front-load pays for itself
  within the first couple of output tokens.
- **CPU, fp32, batch 1.** These CPU absolute tok/s are compute-bound and this impl runs fp32;
  the **ratios** are the deliverable. **Measured on GPU (RTX 4090), the structural wins do *not*
  carry over at batch 1** — the model is so small that a full-buffer pass (~0.6 ms) is already
  free, so the bottleneck shifts to host-loop/dispatch latency and KV-cache/jump-forward stop
  compounding (KV 1.1×, KV+JF < JF). This was the opposite of what this note originally predicted;
  see `../../GPU_NOTES.md` for the on-device numbers, the batch-throughput story, and the two
  benchmark bugs (encoder recompilation + async-dispatch timing) the GPU run surfaced and fixed.
- **All 10 tools every call** → ~584 encoder tokens, so cross-attention over ~600 positions is a
  real per-step cost. ToolRAG (top-k tools, per `ROADMAP.md`) would shrink the encoder and the
  cross-KV, lifting both prefill and generation throughput further.
- **Jump-forward is lossless.** Forced runs have exactly one legal token, so injecting them
  changes nothing about the output (same property as the `f7c5864c` llama.cpp commit); it only
  removes model passes.
